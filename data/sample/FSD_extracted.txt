1. Introduction
1.1 Purpose
This Functional Specification Document (FSD) defines the functional and non-functional requirements for a data integration pipeline that ingests data from heterogeneous sources and formats, normalizes it into a common representation, and applies AI-agent-assisted transformation, mapping, and join logic to produce a unified, discrepancy-free output. The document is intended to translate the architectural concepts already agreed in internal discussion into a build-ready specification for engineering, QA, and platform teams.
1.2 Scope
This specification covers the design of a batch-and-streaming-capable data integration engine composed of the components listed in Section 3. It is scoped as follows:
In Scope
Out of Scope (this phase)
Ingestion from structured (CSV, RDBMS), semi-structured (API/JSON), and streaming sources
Building a proprietary distributed execution engine (Spark/Flink will be used, not built)
Canonical schema/type registry and format normalization
Full ontology/knowledge-graph product surface (only the integration hooks are in scope)
AI agent for source identification, field mapping inference, join inference, and transform generation
Multi-tenant SaaS deployment; this phase targets single-tenant internal deployment

Natural-language BI/reporting layer on top of the output data

Automated data-quality remediation (auto-fix); this phase flags, does not auto-correct
Versioning, proposal/diff review, and controlled deployment of pipeline logic
Real-time collaborative multi-user editing of the same pipeline graph

3. System Overview
3.1 Design Principles
Engine-agnostic core: Pipeline logic is captured as an Intermediate Representation, decoupled from the execution engine, so batch (Spark) and streaming (Flink) share the same logical plan.
Contract-driven output: Every output dataset is validated continuously against a required schema, not only at the end of a run.
Agent proposes, human disposes: The AI agent generates candidate mappings, joins, and transforms; anything below a confidence threshold is routed to mandatory human review before execution.
Full provenance: Every field and row in the output is traceable to its source and the exact rule/inference that produced it.
Change safety: Pipeline modifications are proposed, diffed against the current live version, and explicitly deployed — never silently overwritten.

5. AI Agent Orchestrator — Detailed Behavior
The agent is the highest-risk and most novel component in this system, since it makes semantic judgments (e.g., "this field means the same thing as that field") rather than purely syntactic ones. This section defines its operating stages and the mandatory confidence-scoring/HITL policy referenced throughout Section 4.
5.1 Processing Stages
Stage
Name
Behavior
1
Source Identification
Parse the user's natural-language request; match intent against catalogued datasets/systems using metadata and prior usage; return ranked candidate sources.
2
Mapping Inference
For each candidate source, propose field-to-canonical mappings using name similarity, type compatibility, and value-distribution profiling.
3
Join Inference
Propose join keys and join type across selected sources using key-cardinality analysis, referential patterns, and value-overlap sampling.
4
Transform Generation
Generate IR-level operations that satisfy the user's stated intent (filters, derivations, aggregations).
5
Confidence Scoring
Attach a 0–1 confidence score to every mapping, join, and transform, computed from the evidence used in stages 2–4.
6
Routing
Proposals at or above the confidence threshold flow directly to Preview; proposals below threshold are flagged and require HITL approval before Preview/execution.

5.2 Confidence & Risk Policy
Risk is not uniform across agent decisions. The policy below reflects that field-mapping errors are usually caught by type checking, while join errors are semantic and can pass type checking while still being wrong.
Agent Decision
Risk Level
Rationale
Policy
Source identification
Low
Wrong dataset is usually obvious in preview
Auto-proceed; shown in UI for confirmation
Mapping inference
Medium
Type checker catches most hard failures; semantic mismatches can slip through
Auto-proceed above 0.85 confidence; else HITL
Join inference
High
Two well-typed columns can be joinable and still semantically wrong
HITL required below 0.95 confidence; always shown in Preview regardless of score
Transform generation
Medium
Logic errors are checkable via preview/dry-run diffing
Auto-proceed above 0.85 confidence; else HITL

5.3 Non-Negotiable Guardrails
The agent shall never execute a write to a production output without passing through Type Checker, Contract Validator, and (where applicable) HITL approval.
Every agent decision shall be persisted with its confidence score and evidence, independent of whether it required human review, to support later audit.
A rejected agent proposal shall not be silently retried with the same evidence; it shall require either new evidence or explicit human override.

7. End-to-End Data Flow — Worked Example
Illustrative walkthrough for our companion practice pipeline (modeled on Palantir Foundry’s public "Building Your First Pipeline" tutorial), for the representative request: "Clean and join products, customers, and transactions into a customer lifetime value dataset."
Step
Action
1
User submits the request: “Clean and join products, customers, and transactions into a customer lifetime value dataset.”
2
Agent (Source ID stage) identifies products.csv, customers.json, and transactions.json as candidate sources and confirms with the user.
3
Ingestion Layer connects to all three sources and pulls raw data in native format (CSV, nested JSON, JSON).
4
Agent (Mapping Inference) proposes field mappings to the canonical Product, Customer, and Transaction schemas — including flattening the Customer address struct into flat street/city/state fields; mappings above 0.85 confidence auto-apply, others queue for review.
5
Normalization Engine applies the approved mappings: trims whitespace on product_name, casts price and units from string to numeric, parses the transaction_date string into a timestamp, and drops residual ingestion artifact columns.
6
Agent (Join Inference) proposes joining transactions to products on product_id, with a confidence score; because join risk is High, this always routes to the HITL Preview regardless of score.
7
Reviewer inspects the Preview and notices row-count skew (172 joined rows vs. 50 source rows) — exactly the kind of semantic error type checking cannot catch on its own, since product_id and price are both well-typed but product_id is not actually unique.
8
Reviewer rejects the proposed join key and directs the agent to rejoin on product_variation_id instead, which uniqueness checking confirms is a true primary key.
9
Type Checker and Contract Validator confirm the corrected IR is type-safe and satisfies the required output schema for “customer_lifetime_value.”
10
Execution Engine (Spark, given batch volume) runs the validated IR: joins transactions → products → customers, then aggregates (group by customer_id, sum revenue = price × units).
11
Output dataset is produced with full field- and row-level provenance recorded, including which join key was used and that it was corrected via HITL review.
12
Output is optionally mapped to the Customer object type in the Common Model/Ontology layer.
13
Change is proposed, diffed against the current Main pipeline, reviewed, and explicitly deployed.

10. Assumptions, Dependencies & Constraints
10.1 Assumptions
Source systems expose stable, queryable interfaces (DB access, API, or file drop) — no reverse-engineering of undocumented formats.
An initial canonical schema for at least one business domain will be defined collaboratively before agent training/tuning begins — piloted via the Customer domain in the companion products/customers/transactions practice pipeline (Section 7).
Sufficient labeled or historical mapping/join examples exist, or will be created, to tune the agent's inference confidence scoring.
10.2 Dependencies
Distributed execution engine (Spark) and, if streaming is prioritized, a stream processor (Flink/Kafka Streams).
Secrets management service for source credentials.
Identity/RBAC provider for role-based access control.
10.3 Constraints
Phase 1 targets single-tenant, internal deployment only (see Section 1.2).
Real-time multi-user co-editing of the same pipeline branch is out of scope; branch-based isolation is the concurrency model.
Auto-remediation of data-quality issues is out of scope; the system flags issues for human resolution.

In Scope | Out of Scope (this phase)
Ingestion from structured (CSV, RDBMS), semi-structured (API/JSON), and streaming sources | Building a proprietary distributed execution engine (Spark/Flink will be used, not built)
Canonical schema/type registry and format normalization | Full ontology/knowledge-graph product surface (only the integration hooks are in scope)
AI agent for source identification, field mapping inference, join inference, and transform generation | Multi-tenant SaaS deployment; this phase targets single-tenant internal deployment
Confidence scoring and human-in-the-loop review for agent-generated logic | Natural-language BI/reporting layer on top of the output data
Type checking, schema/contract validation, provenance and lineage tracking | Automated data-quality remediation (auto-fix); this phase flags, does not auto-correct
Versioning, proposal/diff review, and controlled deployment of pipeline logic | Real-time collaborative multi-user editing of the same pipeline graph
Term | Definition
DAG | Directed Acyclic Graph — the pipeline execution graph with no circular dependencies
IR | Intermediate Representation — the engine-agnostic logical plan (Filter, Join, Cast, Map, etc.) compiled from the visual/graph pipeline
Ontology | A semantic layer mapping normalized data to business objects (e.g., Supplier, Transaction) and their relationships
Common Model | The canonical, format-agnostic schema all sources are normalized into before transformation
Agent | The AI orchestration component that infers sources, mappings, joins, and generates transform logic
Confidence Score | A numeric estimate (0–1) of the agent's certainty in a given inferred mapping or join
HITL | Human-In-The-Loop — a mandatory human review/approval checkpoint before low-confidence logic executes
Provenance | Metadata recording the origin and derivation path of every field/row in the output dataset
Contract | The required output schema (column set, types, nullability) an output dataset must satisfy
FR | Functional Requirement
NFR | Non-Functional Requirement
Component | Responsibility
Ingestion Layer | Pluggable connectors that pull raw data from batch and streaming sources in native format
Schema & Type Registry | Canonical type system (e.g., Timestamp, GeometryCol, PhoneNumber) all sources map onto
Normalization / Mapping Engine | Per-source transform chains that cast raw fields into the canonical schema
Union / Merge Stage | Combines normalized sources into a single dataset once schemas are aligned
AI Agent Orchestrator | Identifies sources, infers field mappings and joins, and generates transform logic with confidence scores
Intermediate Representation (IR) | Engine-agnostic logical plan (Filter, Join, Cast, Map, Aggregate) compiled from the pipeline graph
Type Checker | Statically validates that IR operations are type-safe before execution
Contract / Schema Validator | Confirms the projected output satisfies the required output schema
Preview & HITL Gate | Renders a sample of pipeline output and blocks execution on low-confidence agent decisions until reviewed
Execution Engine | Compiles and runs the IR on SQL, Spark, or Flink depending on volume/latency needs
Provenance & Lineage Tracker | Captures the origin and derivation path of every field and row
Common Model / Ontology Layer | Maps normalized datasets to semantic business objects and relationships
Versioning / Proposal & Diff System | Branches, diffs, and reviews pipeline logic changes prior to deployment
Deployment Module | Publishes reviewed pipeline changes and (re)builds target outputs
Monitoring & Alerting | Tracks run health, data-quality metrics, and SLA breaches
Security & Access Control | Enforces authentication, authorization, and data-access policy across the pipeline

Stage | Name | Behavior
1 | Source Identification | Parse the user's natural-language request; match intent against catalogued datasets/systems using metadata and prior usage; return ranked candidate sources.
2 | Mapping Inference | For each candidate source, propose field-to-canonical mappings using name similarity, type compatibility, and value-distribution profiling.
3 | Join Inference | Propose join keys and join type across selected sources using key-cardinality analysis, referential patterns, and value-overlap sampling.
4 | Transform Generation | Generate IR-level operations that satisfy the user's stated intent (filters, derivations, aggregations).
5 | Confidence Scoring | Attach a 0–1 confidence score to every mapping, join, and transform, computed from the evidence used in stages 2–4.
6 | Routing | Proposals at or above the confidence threshold flow directly to Preview; proposals below threshold are flagged and require HITL approval before Preview/execution.
Agent Decision | Risk Level | Rationale | Policy
Source identification | Low | Wrong dataset is usually obvious in preview | Auto-proceed; shown in UI for confirmation
Mapping inference | Medium | Type checker catches most hard failures; semantic mismatches can slip through | Auto-proceed above 0.85 confidence; else HITL
Join inference | High | Two well-typed columns can be joinable and still semantically wrong | HITL required below 0.95 confidence; always shown in Preview regardless of score
Transform generation | Medium | Logic errors are checkable via preview/dry-run diffing | Auto-proceed above 0.85 confidence; else HITL

Step | Action
1 | User submits the request: “Clean and join products, customers, and transactions into a customer lifetime value dataset.”
2 | Agent (Source ID stage) identifies products.csv, customers.json, and transactions.json as candidate sources and confirms with the user.
3 | Ingestion Layer connects to all three sources and pulls raw data in native format (CSV, nested JSON, JSON).
4 | Agent (Mapping Inference) proposes field mappings to the canonical Product, Customer, and Transaction schemas — including flattening the Customer address struct into flat street/city/state fields; mappings above 0.85 confidence auto-apply, others queue for review.
5 | Normalization Engine applies the approved mappings: trims whitespace on product_name, casts price and units from string to numeric, parses the transaction_date string into a timestamp, and drops residual ingestion artifact columns.
6 | Agent (Join Inference) proposes joining transactions to products on product_id, with a confidence score; because join risk is High, this always routes to the HITL Preview regardless of score.
7 | Reviewer inspects the Preview and notices row-count skew (172 joined rows vs. 50 source rows) — exactly the kind of semantic error type checking cannot catch on its own, since product_id and price are both well-typed but product_id is not actually unique.
8 | Reviewer rejects the proposed join key and directs the agent to rejoin on product_variation_id instead, which uniqueness checking confirms is a true primary key.
9 | Type Checker and Contract Validator confirm the corrected IR is type-safe and satisfies the required output schema for “customer_lifetime_value.”
10 | Execution Engine (Spark, given batch volume) runs the validated IR: joins transactions → products → customers, then aggregates (group by customer_id, sum revenue = price × units).
11 | Output dataset is produced with full field- and row-level provenance recorded, including which join key was used and that it was corrected via HITL review.
12 | Output is optionally mapped to the Customer object type in the Common Model/Ontology layer.
13 | Change is proposed, diffed against the current Main pipeline, reviewed, and explicitly deployed.

Failure Scenario | System Behavior | Notification
Source connection failure | Isolate failing source; continue ingesting from remaining sources; mark run partially complete | Alert source owner + pipeline owner
Schema mismatch at Union | Block merge; surface exact column(s)/type(s) in conflict at the offending node | Inline UI error; no silent drop
Type-check failure | Block deployment/execution; highlight failing operation in graph | Inline UI error
Contract validation failure (missing required column) | Block deployment; show required-vs-actual column diff | Inline UI warning (e.g., "37/39 required columns")
Low-confidence agent proposal | Route to HITL queue; do not auto-execute | Notify assigned reviewer
Execution/runtime failure | Halt run; report failing node and error detail; retry per policy | Alert pipeline owner and on-call
Post-deployment data-quality drift | Flag metric breach; do not auto-roll-back by default (configurable) | Alert pipeline owner
